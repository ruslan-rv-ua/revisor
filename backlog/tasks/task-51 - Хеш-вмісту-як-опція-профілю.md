## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Метадані (розмір, дата зміни, атрибути) не помічають рідкісних випадків, коли вміст змінився, а метадані лишилися ті самі. Хеш вмісту дає надійність, потрібну передусім для другорядного сценарію — перевірки цілісності. Знімок із хешем повільніший, бо доводиться читати кожен файл, тому хеш вмикають у профілі.

Етап: 0.6 (m-7). 2026-11-14 перенесено з 0.5: це найглибша зміна віхи, а формат даних має усталитися лише до 1.0.

Вирішено з користувачем (2026-11-14):
- **Алгоритм — SHA-256.** Його типово рахує Get-FileHash у Windows і публікують виробники програм, ним же README revisor радить перевіряти завантажений exe, тож хеш зі знімка можна звірити з опублікованим.
- **Опція профілю** — прапорець у вікні профілю, типово вимкнений; зберігається в базі профілю (ADR-0006).
- **Де хешу немає хоча б з одного боку** (хеш увімкнули між знімками, файл не вдалося прочитати), файл порівнюють, як зараз, за метаданими; якщо хешу немає в цілому знімку, порівняння попереджає про це, як про різні теки чи винятки (TASK-10).
- **Файли лише в хмарі** (OneDrive тощо) revisor не відкриває й не хешує, як уже не відкриває їх заради версії exe чи dll: Microsoft пише, що читання такого файлу змушує отримати вміст із віддаленого сховища.
- **Показ.** «Що змінилося» — «вміст»; «Подробиці» — хеш «було → стало»; CSV — колонки sha256_before і sha256_after; текстовий звіт — без значень хешу. revisor-cli рахує хеш за прапорцем профілю.

Походження: бриф продукту (перевірка цілісності); обговорення 2026-11-14.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 У вікні профілю є прапорець «Рахувати хеш вмісту (знімок повільніший)» (Compute content hashes (slower snapshots)), типово вимкнений; він зберігається в профілі.
- [ ] #2 Коли прапорець увімкнено, знімок зберігає хеш SHA-256 кожного файлу, який вдалося прочитати.
- [ ] #3 Файли, що лежать лише в хмарі (OneDrive тощо), revisor не відкриває й хешу для них не рахує; зайняті й недоступні файли теж лишаються без хешу. Знімок від цього не зупиняється.
- [ ] #4 Коли обидва знімки мають хеш файлу, а хеші різні, файл позначено зміненим, навіть якщо розмір, дата й атрибути збіглися; «Що змінилося» тоді називає «вміст».
- [ ] #5 Де хешу немає хоча б з одного боку, файл порівнюють, як зараз, за метаданими. Якщо хешу немає в усьому ранішому чи пізнішому знімку, порівняння попереджає про це так само, як про різні теки чи винятки.
- [ ] #6 «Подробиці» показують хеш SHA-256 «було → стало»; для файлу без хешу — «не пораховано (не враховано)», як для непрочитаної версії.
- [ ] #7 CSV має пару колонок sha256_before і sha256_after; текстовий звіт називає зміну вмісту без самих значень хешу.
- [ ] #8 Поки рахуються хеші, рядок прогресу каже про це й показує, скільки вже зроблено; «Скасувати» спрацьовує й посеред великого файлу.
- [ ] #9 revisor-cli рахує хеш за прапорцем профілю, без окремого параметра; його звіт і CSV — як у пункті 7.
- [ ] #10 Старі знімки й профілі відкриваються, як і раніше.
- [ ] #11 Тести перевіряють хеш відомих даних, порівняння з хешем і без нього з одного боку, пропуск файлів у хмарі, попередження й колонки CSV.
- [ ] #12 Виміряно, у скільки разів довший знімок із хешем на типовому профілі, і число записано в задачі.
- [ ] #13 ADR описує вибір SHA-256 і зберігання хешу; бриф, глосарій і README обома мовами описують опцію.
