## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Узгоджено з користувачем 2026-10-30 (по одному питанню).

1. Гілка `feature/task-3-scanner` від `develop`.
2. Модуль `scan` у `revisor-core` (ADR-0005), залежність `windows-sys`.
3. Обхід теки: відкриваємо лише теку (`CreateFileW` з `FILE_FLAG_BACKUP_SEMANTICS`) і читаємо вміст пакетами через `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)`: розмір, дати створення й зміни, атрибути, 128-бітний File ID і тег reparse — без відкриття кожного файлу.
4. Паралельний обхід: черга тек, кількість потоків — параметр (1 = послідовно). Вимірюємо 1 потік і кілька.
5. Результат — дерево в пам'яті: `Vec` записів з індексом батька, ім'ям, видом (тека/файл/посилання), атрибутами; стан «недоступно» на записі (ADR-0003).
6. Версія exe/dll (за розширенням, без урахування регістру): числова FileVersion із `VS_FIXEDFILEINFO` через `GetFileVersionInfoW`/`VerQueryValueW`. Час на читання версій рахуємо окремо; опція вимкнути читання версій.
7. Reparse point (junction, symlink): ціль читаємо `FSCTL_GET_REPARSE_POINT`, усередину не заходимо.
8. Недоступні теки/файли — запис із позначкою, обхід триває.
9. Довгі шляхи — префікс `\\?\` (і `\\?\UNC\`).
10. Скасування — `Arc<AtomicBool>`, перевірка перед кожною текою; результат — помилка «скасовано».
11. Тести на тимчасових теках: атрибути, вкладеність, довгий шлях, junction, недоступна тека, скасування, версія exe.
12. Приклад `crates/revisor-core/examples/scan_bench.rs`: корінь, кількість потоків, без версій; друкує кількість записів, час, частку часу на версії, пікову пам'ять (`GetProcessMemoryInfo`). Виміри на C:\ — у нотатки.
13. test, clippy, fmt; рев'ю; коміти англійською; злиття в `develop` — за згодою користувача.

Уточнення під час реалізації: теку відкриваємо через `std::fs::OpenOptions` з `access_mode`/`custom_flags` замість прямого `CreateFileW` (дескриптор закривається сам); скасування — `&AtomicBool` (власник прапорця вирішує, як його ділити). Тест symlink пропускається без Developer Mode.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Сканер — модуль `revisor_core::scan` (`crates/revisor-core/src/scan.rs`, FFI — `scan/sys.rs`, тести — `scan/tests.rs`). API: `scan(root, &ScanOptions { threads, read_versions }, &AtomicBool) -> Result<Scan, ScanError>`. `Scan.entries` — дерево, сплощене у `Vec<Entry>`: корінь — запис 0, у кожного запису індекс батька, ім'я (`Box<OsStr>`), вид Dir/File/Link, позначка `inaccessible`, атрибути, розмір, дати створення й зміни (FILETIME), 128-бітний File ID, версія `[u16; 4]`, ціль посилання. Діти теки лежать поруч. Розмір `Entry` — 96 Б.

Як працює: теку відкриваємо через `OpenOptions` (FILE_LIST_DIRECTORY, FILE_FLAG_BACKUP_SEMANTICS) і читаємо пакетами по 64 КБ через `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)` — файли не відкриваються. Паралельний обхід: стек тек під `Mutex` + `Condvar`, записи додаються в спільний `Vec` під `Mutex` (один лок на теку). Посилання — будь-який reparse point із бітом name surrogate (junction, symlink, WSL-symlink…); ціль читаємо `FSCTL_GET_REPARSE_POINT` (PrintName, інакше SubstituteName без `\??\`), усередину не заходимо. Інші reparse point (напр. хмарні теки OneDrive) обходимо як звичайні теки. Версія — лише для `.exe`/`.dll` (без урахування регістру), `GetFileVersionInfoExW(FILE_VER_GET_NEUTRAL)` + `VerQueryValueW("\\")`. Довгі шляхи — `\\?\` / `\\?\UNC\` від кореня. Скасування перевіряється перед кожною текою та перед кожним читанням версії.

«Недоступно»: тека, яку не вдалося відкрити чи дочитати (діти, прочитані до помилки, лишаються); посилання, ціль якого не прочиталася; exe/dll, версію якого не дали прочитати (ACCESS_DENIED, SHARING_VIOLATION, LOCK_VIOLATION). Файл без ресурсу версії чи не PE — просто без версії. Корінь, який не відкривається, — помилка `ScanError::Root`.

Тести (14, `cargo test -p revisor-core`): метадані проти `std::fs::metadata`, унікальність File ID, версія копії kernel32.dll і «фальшивого» exe, junction (через `mklink /J`) без заходу всередину, тека з забороною перегляду (`icacls /deny *S-1-1-0:(RD)`) — позначена, сусіди скануються, шлях > 260 символів (разом із версією dll на ньому), однакове дерево для 1 і 8 потоків, скасування, відсутній корінь, `verbatim`, розбір буфера reparse. Тест символьного посилання на цьому комп'ютері пропускається (без Developer Mode symlink не створити) — формат буфера symlink перевірено юніт-тестом розбору.

## Виміри (2026-10-30, `scan_bench`, release-профіль проєкту: opt-level "z", LTO)

Запуск: `cargo run --release -p revisor-core --example scan_bench -- <корінь> [--threads N] [--no-versions]`. Без прав адміністратора. Пам'ять — пік процесу: working set і private commit (`GetProcessMemoryInfo`). 8 потоків — типове значення (кількість ядер, не більше 8).

C:\Users — 535 665 записів (3 570 exe/dll): 8 потоків 2,0 с (з версіями й без — однаково), 1 потік 5,5 с (версії 13%); пік 84–124 / 95–169 МіБ.
C:\Windows — 338 521 запис (44 852 exe/dll): 8 потоків 2,9–3,0 с з версіями, 1,4 с без (версії ~41–51%); пік 80 / 100 МіБ.

Висновки:
- Обхід без версій: ~2,1 млн записів за 4,8 с (8 потоків) / 15,4 с (1 потік) на теплому кеші. Паралельність дає ×2,6–3,2 — варто тримати в MVP.
- Частка версій exe/dll на теплому кеші — близько третини часу (1 потік: 7,2 з 22,3 с). На холодному першому проході версії — майже весь час (~95%, 286 с): кожне відкриття exe/dll — холодне читання з диска і, ймовірно, перевірка антивірусом (Defender) на відкритті; гіпотезу про Defender не перевіряли. Це головний ризик швидкості: перший знімок після перезавантаження може тривати хвилини.
- Пам'ять: ~96 Б на запис + ~25 Б імені, але пік commit 380–680 МіБ на 2,1 млн записів (≈180–320 Б на запис) через подвоєння ємності `Vec` (у момент перевиділення живуть старий і новий буфери, ємність 4 194 304 × 96 Б = 384 МіБ) і чергу тек. На ~1 млн записів очікуємо ~200–300 МіБ піку. Зменшити можна (зберігання шматками, компактніший запис) — окреме рішення, якщо цифри не влаштують.
- Розкид кількості записів між проходами (±10) — файли, що змінюються під час сканування.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Додано сканер у ядро — `revisor_core::scan` (`crates/revisor-core/src/scan.rs`, `scan/sys.rs`) — і приклад вимірів `crates/revisor-core/examples/scan_bench.rs`. Нова залежність ядра — `windows-sys` 0.61 (вже була в lock через wxdragon).

Що збирає: дерево записів (індекс батька, ім'я, вид тека/файл/посилання) з розміром, датами створення й зміни, атрибутами, 128-бітним File ID NTFS, числовою версією exe/dll, ціллю junction/symlink і позначкою «недоступно». Теки читаються пакетами `FileIdExtdDirectoryInfo` без відкриття файлів; обхід паралельний (кількість потоків — параметр), довгі шляхи через `\\?\`, скасування через `AtomicBool`.

Виміри на C:\ (2,13 млн записів, без адміністратора): теплий кеш, 8 потоків — 10,3 с з версіями, 4,8 с без; 1 потік — 22,3 / 15,4 с. Частка версій exe/dll — близько третини часу на теплому кеші, але ~95% на холодному першому проході (286 с). Пік пам'яті — 380–680 МіБ commit на 2,1 млн записів (подвоєння `Vec`). Повна таблиця й висновки — у нотатках.

Перевірки: 14 тестів, clippy `-D warnings`, fmt --check — чисті. Бриф і ADR не змінювалися: рішення задачі — рівня реалізації.

Ризики й наступне: холодний перший знімок повільний через читання версій (гіпотеза — Defender, не перевірено); пік пам'яті можна зменшити, якщо цифри не влаштують (TASK-6); symlink перевірено лише юніт-тестом розбору буфера; не-NTFS томи (FAT/exFAT) можуть не підтримувати `FileIdExtdDirectoryInfo` — не перевірялось.
