## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Знімки зберігаються в SQLite, окрема база на кожен профіль (ADR-0002), а модель знімка — дерево записів від джерел із номером версії схеми (ADR-0003). Ця задача перевіряє, що така схема витримує ~1 млн записів, і дає цифри для цілей. Схема — основа для MVP.

Вимірюємо і на реальному знімку із задачі сканера, і на записах, згенерованих у коді без створення файлів на диску.

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Узгоджено з користувачем 2026-10-30 (по одному питанню).

1. Гілка `feature/task-4-store` від `develop`.
2. Модуль `revisor_core::store`, залежність `rusqlite` з feature `bundled` (SQLite вкомпільовано в exe).
3. Схема v1 (`PRAGMA user_version = 1`; база новішої версії → помилка):
   - `snapshot(id, taken_at, comment)`;
   - `entry(snapshot_id, source, idx, parent, name, kind, inaccessible)`, PK (snapshot_id, source, idx), WITHOUT ROWID — спільне дерево; source 1 = файлова система; kind 0 — контейнер, 1 — елемент;
   - `fs_entry(snapshot_id, idx, attributes, size, created, modified, file_id BLOB(16), version INTEGER — упакований u64, link_target)`, WITHOUT ROWID — атрибути джерела 1:1. Посилання — елемент із link_target NOT NULL ('' — ціль невідома).
   - Шлях — ім'я + номер батька. Ім'я — TEXT (UTF-8), а невалідне UTF-16 — BLOB сирого UTF-16LE у тій самій колонці.
4. API: `Store::open`, `save(comment, &[Entry], &AtomicBool)` однією транзакцією, `load(id)`, `list()`, `delete(id)` (явні DELETE в одній транзакції), `vacuum()`. Журнал — типовий rollback (DELETE); WAL — лише прапорець бенча для порівняння.
5. Генератор синтетичного дерева `scan::synthetic(n)` (pub, для тестів і бенча).
6. Тести (TDD): версія схеми; round-trip усіх полів (невалідне UTF-16 ім'я, посилання без цілі, версія); новіша версія → помилка; скасування → без слідів; вбитий дочірній процес (чекаємо появи `-journal`, вбиваємо) → попередній знімок цілий, часткового немає; delete + vacuum зменшує файл.
7. Приклад `store_bench`: `--scan <корінь>` або `--generate N`, `--wal`; час запису й читання, розмір бази; другий знімок → видалити перший → розмір до/після VACUUM і час VACUUM. Заміри: C:\ і 1 млн згенерованих, rollback і WAL.
8. test, clippy, fmt; рев'ю; коміт англійською; злиття в `develop` — за згодою користувача.

Уточнення після рев'ю (за згодою користувача): `snapshot.id` — `INTEGER PRIMARY KEY AUTOINCREMENT`, щоб id видалених знімків не повторювались; тест скасування переривав запис уже посеред транзакції (прапорець ставить інший потік); у WAL бенч робить `wal_checkpoint(TRUNCATE)` перед кожним заміром розміру.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Сховище — модуль `revisor_core::store` (`crates/revisor-core/src/store.rs`, тести — `store/tests.rs`), залежність `rusqlite` 0.41 з `bundled`. API: `Store::open(path)`, `save(comment, &[Entry], &AtomicBool) -> id`, `load(id) -> Vec<Entry>`, `list() -> Vec<SnapshotInfo>`, `delete(id)`, `vacuum()`; помилки — `StoreError { Sqlite, NewerSchema(v), Cancelled }`.

Схема v1 (`PRAGMA user_version = 1`; створюється в одній транзакції з номером версії; база новішої версії → `NewerSchema`):
- `snapshot(id INTEGER PRIMARY KEY AUTOINCREMENT, taken_at — Unix мс, comment)`;
- `entry(snapshot_id, source, idx, parent, name, kind, inaccessible)`, PK (snapshot_id, source, idx), WITHOUT ROWID — спільне дерево для всіх джерел (source 1 = файлова система; kind 0 — контейнер, 1 — елемент);
- `fs_entry(snapshot_id, idx, attributes, size, created, modified, file_id BLOB(16), version — 4×u16 у одному INTEGER, link_target)`, WITHOUT ROWID. Посилання (junction/symlink) — елемент із link_target NOT NULL; '' — ціль невідома.
- Ім'я й ціль посилання — TEXT (UTF-8), а невалідне UTF-16 (непарні сурогати) — BLOB сирого UTF-16LE в тій самій колонці.

`save` — одна транзакція; скасування перевіряється кожні 4096 записів, вихід через `Cancelled` відкочує транзакцію. `delete` — три явні DELETE в одній транзакції. Генератор синтетичного дерева — `scan::synthetic(n)` (детермінований; у кожної теки 2 підтеки й 10 файлів, частка тек ≈ як на реальному диску; dll/exe з версією).

Тести (9 у `store`, 1 у `scan`; усього в ядрі 23 + 1 ignored-допоміжний): версія схеми у файлі; новіша версія → помилка; round-trip усіх полів (крайні значення розміру й дат, версія, недоступні теки й посилання, посилання без цілі, ім'я з непарним сурогатом); знімки не змішуються; скасування посеред запису 1 млн записів → у базі лише попередній знімок; delete → знімка немає, файл не зменшився, після VACUUM — менше 10%; id видаленого знімка не повторюється; **вбитий процес**: тест запускає власний тестовий exe дочірнім процесом, чекає появи `profile.db-journal` (транзакція відкрита), вбиває його й перевіряє, що після відкриття бази є лише попередній знімок (SQLite відкотив гарячий журнал).

## Виміри (2026-10-30, `store_bench`, release-профіль проєкту, SSD, без адміністратора)

Запуск: `cargo run --release -p revisor-core --example store_bench -- (--scan <корінь> | --generate N) [--wal] [--db <шлях>]`. Сценарій: запис знімка → читання → запис другого такого самого → видалення першого → VACUUM. Розмір у WAL — після `wal_checkpoint(TRUNCATE)`.

| Вхід | Журнал | Запис | Читання | Розмір 1 знімка | 2 знімки | Видалення | VACUUM | Після VACUUM | Повернуто |
|---|---|---|---|---|---|---|---|---|---|
| 1 млн згенерованих | rollback | 1,66 с | 0,69 с | 92,5 МіБ (97 Б/запис) | 187,4 МіБ | 0,57 с | 0,72 с | 83,9 МіБ | 103,5 МіБ |
| 1 млн згенерованих | WAL | 2,0 с | 0,73 с | 92,5 МіБ | 187,4 МіБ | 0,64 с | 0,6 с | 83,9 МіБ | 103,5 МіБ |
| C:\ — 2,13 млн | rollback | 3,8–6,5 с | 1,6–3,0 с | 217,5 МіБ (107 Б/запис) | 439,7 МіБ | 1,3–1,8 с | 1,6–2,5 с | 196,8 МіБ | 242,9 МіБ |
| C:\ — 2,13 млн | WAL | 7,6–7,9 с | 2,9–3,1 с | 217,6 МіБ | 439,9 МіБ | 2,5–2,8 с | 2,4–3,1 с | 196,9 МіБ | 243,0 МіБ |

C:\ — 4 прогони rollback і 2 WAL; розкид, ймовірно, від фонової роботи диска (перший прогін — одразу після холодного сканування).

Висновки:
- На ~1 млн записів: запис ≈ 1,7–3 с, читання ≈ 0,7–1,4 с, база ≈ 95–105 МіБ на знімок (~100 Б на запис: 97 Б на згенерованих, 107 Б на реальних — довші імена). Швидше за сканування з версіями (TASK-3: 10 с на 2,1 млн на теплому кеші).
- Узагальнення «спільна таблиця + таблиця джерела» коштує два вставлення на запис, але цифри прийнятні.
- WAL не дає виграшу для одного великого запису: на C:\ він помітно повільніший (≈ 7,7 проти 3,8–6,5 с). Лишаємо типовий rollback-журнал — один файл у теці `data`.
- VACUUM повертає все місце видаленого знімка (≈ 103,5 МіБ на 1 млн, 243 МіБ на 2,13 млн) за 0,6–3 с. Після VACUUM знімок займає на ~10% менше, ніж одразу після запису (сторінки B-дерева щільніші), тож розмір бази залежить від того, коли востаннє робили VACUUM.
- Видалення знімка без VACUUM розміру файлу не змінює (вільні сторінки використовуються наступними знімками) — VACUUM варто робити після видалення (ADR-0002, ризики).

Не вимірювали: вплив SQLite на розмір exe (застосунок `revisor` ще не використовує сховище, тож LTO його викидає) — виміряємо, коли сховище підключиться до застосунку.

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Додано сховище знімків у ядро — `revisor_core::store` (`crates/revisor-core/src/store.rs`) на `rusqlite` 0.41 з вкомпільованою SQLite — генератор синтетичного дерева `scan::synthetic(n)` і приклад вимірів `crates/revisor-core/examples/store_bench.rs`.

Схема v1 (`user_version = 1`) відповідає ADR-0003: спільне дерево `entry` (знімок, джерело, номер, батько, ім'я, вид контейнер/елемент, недоступно) і атрибути файлової системи в `fs_entry` 1:1; шлях — ім'я + батько; невалідні UTF-16 імена зберігаються без втрат як BLOB. Знімок пишеться однією транзакцією; скасування й аварійне завершення процесу не лишають часткового знімка (перевірено тестами, зокрема з вбитим дочірнім процесом). id знімків не повторюються (AUTOINCREMENT).

Виміри: 1 млн згенерованих записів — запис 1,7 с, читання 0,7 с, 92,5 МіБ; реальний знімок C:\ (2,13 млн) — запис 3,8–6,5 с, читання 1,6–3 с, 217,5 МіБ (~100 Б на запис). VACUUM після видалення знімка повертає все його місце (103,5 / 243 МіБ) за 0,6–3 с. WAL не швидший — лишаємо rollback-журнал. Повна таблиця — у нотатках.

Перевірки: `cargo test --workspace` (23 тести + 1 допоміжний ignored), clippy `-D warnings`, fmt --check — чисті. Рев'ю (стандарти й специфікація) — зауваження виправлено. Бриф і ADR не змінювались: рішення задачі — рівня реалізації.

Ризики й наступне: вплив SQLite на розмір exe ще не виміряно (сховище не підключено до застосунку); міграцій схеми поки немає — лише відмова відкривати новішу базу; база без revisor-схеми з `user_version = 0` дає загальну помилку SQLite.
