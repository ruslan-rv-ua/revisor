## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Узгоджено з користувачем 2026-10-30 (по одному питанню):
- лише дата створення відрізняється → змінено;
- атрибут «архівний» (0x20) ігноруємо;
- у тек дату зміни ігноруємо (тека змінена лише за атрибутами чи датою створення);
- додана/видалена тека → у різниці кожен запис її піддерева;
- недоступні — окремий перелік поруч зі змінами; «порожня різниця» = немає змін;
- імена зіставляємо без урахування регістру (як NTFS), зміна лише регістру імені → змінено.

1. Гілка `feature/task-5-diff` від `develop`.
2. Модуль `revisor_core::diff` (`crates/revisor-core/src/diff.rs`, тести — `diff/tests.rs`): `diff(old: &[Entry], new: &[Entry], cancel: &AtomicBool) -> Result<Diff, Cancelled>`.
   - `Diff { changes: Vec<Change>, inaccessible: Vec<Pair> }`; `Change { kind: Added | Removed | Modified, old: Option<u32>, new: Option<u32>, fields }` — `fields` — бітові прапорці змінених полів (ім'я, розмір, дата створення, дата зміни, атрибути, версія, ціль посилання). Порядок — обхід дерева в глибину, діти за ключем імені. Шлях запису будується за ланцюжком батьків (`path(entries, idx)`).
   - Алгоритм: для кожного знімка — індекс дітей за батьком (CSR, O(n)), не покладаючись на суміжність дітей; ключ імені — верхній регістр UTF-16 через `CharUpperBuffW`; корені зіставляються завжди (ім'я кореня не порівнюємо); для пари тек — діти сортуються за ключем і зливаються.
   - Правила: вид змінився (файл ↔ тека ↔ посилання) → видалено + додано; порівнюємо розмір, дату створення, дату зміни (крім тек), атрибути без 0x20, версію, ціль посилання, регістр імені. Поле, невідоме через недоступність (версія недоступного файлу, ціль недоступного посилання), не порівнюємо.
   - Недоступні: запис, недоступний хоча б в одному знімку, іде в перелік недоступних і не стає доданим/видаленим; якщо тека недоступна хоча б з одного боку, її діти, яких немає з другого боку, пропускаються (не відомо, чи вони були), а наявні з обох боків порівнюються звичайно.
   - Скасування — прапорець, перевірка раз на кілька тисяч записів.
3. Тести (TDD): кожне правило окремо на малих деревах; генератор відомих змін над `scan::synthetic` (змінені поля, видалені й додані файли й теки з піддеревами, зміна виду, регістру, цілі посилання, недоступні) → різниця рівно очікувана; той самий знімок → порожня; реальна тимчасова тека (файли, підтеки, junction) сканується двічі, зберігається й завантажується зі SQLite → порожня різниця; скасування.
4. Приклад `diff_bench`: `--scan <корінь>` (сканує двічі) або `--generate N` (другий знімок — із відомими змінами); обидва знімки пишуться в тимчасову базу; потім той самий exe запускається дочірнім процесом лише для «завантажити обидва + порівняти», щоб пікова пам'ять не включала сканування; виводить час завантаження, час порівняння, кількість змін/недоступних і пікову робочу множину та private commit. Заміри: 1 млн згенерованих і реальна тека (C:\ або Program Files).
5. test, clippy, fmt; рев'ю; коміт англійською; злиття в `develop` — за згодою користувача.

Уточнення під час реалізації: ключ імені — `char::to_uppercase` по одному юніту UTF-16 (замість `CharUpperBuffW`: без залежності від user32 і мовних налаштувань); перелік недоступних — тип `Inaccessible { old, new }`; бенч виводить шляхи перших 20 змін, щоб перевірити на око, що зміни на C:\ справжні.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Порівняння — модуль `revisor_core::diff` (`crates/revisor-core/src/diff.rs`, тести — `diff/tests.rs`). API: `diff(old, new, &AtomicBool) -> Result<Diff, Cancelled>`; `Diff { changes: Vec<Change>, inaccessible: Vec<Inaccessible> }`; `Change { kind: Added | Removed | Modified, old, new: Option<u32>, fields: Fields }` — індекси в знімках і бітові прапорці змінених полів (NAME — лише регістр, SIZE, CREATED, MODIFIED, ATTRIBUTES, VERSION, LINK_TARGET); `path(entries, idx)` будує повний шлях. Порядок різниці — обхід дерева в глибину, діти за ключем імені.

Алгоритм: для кожного знімка — індекс дітей за батьком (CSR, O(n)), тож порядок записів не важливий; для пари тек діти обох знімків сортуються за ключем (верхній регістр UTF-16 по одному юніту, як порівнює NTFS; при рівних ключах — за точним іменем) і зливаються. Обхід ітеративний (стек рамок), без рекурсії. Буфери ключів перевикористовуються між теками. Без нових залежностей: верхній регістр — `char::to_uppercase` з відкиданням відображень, що не дають один юніт.

Правила (погоджено з користувачем, перенесено в DRAFT-2):
- корені зіставляються завжди, ім'я кореня не порівнюється;
- вид змінився (файл ↔ тека ↔ посилання) → видалено + додано (з піддеревом);
- змінено: регістр імені, розмір, дата створення, дата зміни (крім тек), атрибути без «архівний» (0x20), версія, ціль посилання; версію й ціль не порівнюємо, якщо запис недоступний хоча б з одного боку (вони тоді невідомі);
- доданий/видалений запис — разом із кожним записом піддерева;
- недоступний хоча б в одному знімку → перелік `inaccessible`, ніколи не додано/видалено (його піддерево з одного боку теж пропускається); відомі поля все одно порівнюються;
- діти теки, недоступної хоча б з одного боку, яких немає з другого боку, пропускаються.

Тести (20 у `diff`; усього в ядрі 43 + 1 ignored-допоміжний): кожне правило окремо на малих деревах (додано/видалено, піддерево, поля, лише дата створення, версія, атрибут A, дата зміни тек, регістр зокрема кирилиці, ціль посилання, зміна виду, недоступні з одного/обох боків, діти недоступної теки, порядок записів, порожні знімки, скасування); **згенеровані відомі зміни** — над `synthetic(50 000)` генератор робить усі види змін (поля, регістр, видалені файли й теки з піддеревами, додані файли й теки, зміна виду, ціль посилання, версія, недоступні файли в старому й теки в новому з пропущеними дітьми, а також «шумові» зміни, яких у різниці бути не повинно: атрибут A, дата зміни тек) і перевіряє, що різниця збігається з очікуваною рівно; **реальна тека** — тимчасове дерево (підтеки, кириличні імена, dll з версією, junction) сканується двічі, обидва знімки зберігаються в SQLite й завантажуються → змін і недоступних немає.

## Виміри (2026-10-30, `diff_bench`, release-профіль проєкту, SSD, без адміністратора)

Запуск: `cargo run --release -p revisor-core --example diff_bench -- (--scan <корінь> | --generate N) [--db <шлях>]`. Обидва знімки спершу пишуться в базу; потім той самий exe запускається дочірнім процесом, що лише завантажує обидва знімки й порівнює їх, — тож пікова пам'ять не містить сканування й запису.

| Вхід | Завантаження обох | Порівняння | Разом | Пік після завантаження (WS / commit) | Пік загалом (WS / commit) | Різниця |
|---|---|---|---|---|---|---|
| 1 млн згенерованих + копія зі змінами (3 прогони) | 1,38–1,40 с | 0,19–0,20 с | 1,58–1,60 с | 252 / 294 МіБ | 272 / 294 МіБ | +1000, ~6666 |
| C:\ — 2,13 млн, два сканування поспіль (2 прогони) | 3,1–3,2 с | 0,56–0,97 с | 3,75–4,1 с | 754 / 1141 МіБ | 754 / 1141 МіБ | 7 і 2 зміни, 127 недоступних |
| C:\Program Files — 13 тис., два сканування | 0,02 с | < 0,01 с | 0,02 с | 12 / 8 МіБ | 12 / 8 МіБ | 0 змін, 2 недоступних |

Перевірка «жодних фальшивих змін» на реальних теках: Program Files — порожня різниця. На C:\ між двома скануваннями (~10–20 с) знайдено 7 і 2 зміни; бенч виводить їхні шляхи — це файли, які справді записувались у цей час (сесія Sentry застосунку Claude, профіль запуску PowerShell), зміни лише дати зміни/розміру. Фальшивих змін (на кшталт тек, атрибута A чи регістру) немає.

Висновки:
- Порівняння саме по собі швидке: 0,2 с на 1 млн записів, 0,6–1 с на 2,1 млн. Основний час — завантаження з SQLite (≈ 0,7 с на 1 млн записів на знімок, як у TASK-4).
- Пам'ять визначає завантаження двох знімків у `Vec<Entry>`: ≈ 125 Б робочої множини на запис (1 млн + 1 млн → 252 МіБ); порівняння додає ≈ 20 МіБ (індекси дітей і результат). На C:\ (2 × 2,13 млн) — 754 МіБ WS і 1,1 ГіБ commit; commit вищий за WS, ймовірно, через подвоєння `Vec` під час `load` (місткість наперед невідома).
- Якщо пам'ять стане проблемою: `load` з `COUNT(*)`/`with_capacity`, компактніший запис (імена в одному буфері замість `Box<OsStr>` на запис), або порівняння потоком з бази без завантаження обох знімків. Для цілей на ~1 млн записів зараз прийнятно.

Не вимірювали: порівняння з паралельністю (не знадобилось); вплив на розмір exe (порівняння ще не підключено до застосунку).

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
Додано порівняння двох знімків у ядро — `revisor_core::diff` (`crates/revisor-core/src/diff.rs`) — і приклад вимірів `crates/revisor-core/examples/diff_bench.rs`.

Порівняння зіставляє записи за шляхом без урахування регістру (як NTFS) злиттям відсортованих дітей кожної пари тек; індекс дітей будується за батьками, тож порядок записів не важливий. Результат — зміни (додано / видалено / змінено з прапорцями полів) у порядку дерева й окремий перелік недоступних. Правила погоджено з користувачем і перенесено в DRAFT-2: дата створення — зміна; атрибут «архівний» і дата зміни тек ігноруються; додана/видалена тека — з кожним записом піддерева; зміна регістру імені — зміна; зміна виду — видалено + додано; недоступні ніколи не стають доданими/видаленими, а невідомі через недоступність поля не порівнюються.

Виміри: 1 млн записів — завантаження обох знімків 1,4 с + порівняння 0,2 с, пік 272 МіБ; реальний C:\ (2 × 2,13 млн) — 3,1 с + 0,6–1 с, пік 754 МіБ WS / 1,1 ГіБ commit. Пам'ять і час визначає завантаження з SQLite, не порівняння. Два сканування Program Files поспіль — порожня різниця; на C:\ — лише справжні зміни (файли, записані між скануваннями). Повна таблиця — у нотатках.

Перевірки: `cargo test --workspace` (43 тести + 1 допоміжний ignored), clippy `-D warnings`, fmt --check — чисті. Інтерфейс не змінювався. Бриф і ADR не змінювались; рішення щодо правил записано в DRAFT-2 (за згодою користувача).

Ризики й наступне: пам'ять на 2 млн записів (~750 МіБ) — можна зменшити (`with_capacity` у `load`, компактніший запис, потокове порівняння); верхній регістр — власна таблиця Unicode через `char::to_uppercase`, може зрідка розходитись із таблицею NTFS для екзотичних літер; критерій DRAFT-2 #3 ще не згадує дату створення й версію (вони є в описі).
